UX DESIGN / SOLANA EDITION

Solanaでは、外部の決済網に頼らずに軽い方式が組める。

EVM版では「ATM改修を最小にする」と引き換えにWalletConnect Payという外部事業者への依存が発生しました。Solanaでは、同じ軽さをSolana Payという公開仕様の自前実装で得られます。手数料も、日本での提供可否の照会も要りません。

本書はv1.0（EVM版）の別冊です。共通部分——事前登録、旅券MRZ読取、ATM画面の骨格、記録要件の扱い——はv1.0をそのまま流用します。ここでは決済部分の差分だけを扱います。

EVM版との主な違い

有利
軽量方式に第三者が要らない Solana Payは公開仕様。DAMSが自分で実装でき、決済手数料も外部事業者の可用性リスクも発生しない。
有利
確定が速い confirmed で約1〜2秒。Baseの1ブロック待ちより短く、ATMの沈黙時間が縮む。
不利
署名に有効期限がある 通常のトランザクションは150スロット（約80〜90秒）で失効する。ATMの操作時間と正面から衝突する。
不利
ガス肩代わりが自明でない EIP-3009では構造上DAMSが必ず送信側になる。Solanaでは手数料負担者の設計を明示的に組む必要がある。

結論を先に書くと、有効期限の問題は「Durable Nonce」で解け、しかもその副産物としてDAMSが署名済みトランザクションを一方的に無効化できる仕組みが手に入ります。これはEVM版にはなかった強い安全性です。

Solana固有の制約

ATMという用途で効いてくる制約が4つあります。順に潰します。

① トランザクションが80〜90秒で失効する

すべてのSolanaトランザクションは recentBlockhash を含み、これは150スロット（約80〜90秒）で失効します。二重支払い防止のための仕組みですが、ATMの操作時間と正面から衝突します。

v1.0で見積もったATM所要時間は約43秒でしたが、これは順調に進んだ場合の数字です。利用者が署名画面で迷えば、あるいはQRの読み取りに手間取れば、90秒は簡単に超えます。そのままではトランザクションが期限切れで落ち、原因不明のエラーとして利用者に返ることになります。

解決策は Durable Nonce です。recentBlockhash の代わりにNonce口座に保存された値を使い、先頭の命令として AdvanceNonceAccount を置く。これで有効期限が消え、誰かがNonceを進めるまでトランザクションは有効なままになります。

副産物として、DAMS側の一方的な無効化手段が手に入る

Nonceを進める権限（authority）はDAMSが持ちます。つまりDAMSはいつでもNonceを進めることで、既に署名済みのトランザクションを一方的に無効化できます。ATM側で障害を検知したとき、利用者の協力なしにその署名を殺せる。EIP-3009では利用者の cancelAuthorization 署名が必要でしたが、Solanaでは要りません。ATMという「止められないインフラ」に載せるうえで、これは大きな利点です。

運用上の注意内容
Nonce口座はプール化1つのNonce口座につき同時に処理できるトランザクションは1件です。ATMセッションごとに1口座を割り当てるプールが必要になります。口座あたりのレント免除に約0.0015 SOLかかるので、同時セッション数×0.0015 SOLが常時ロックされます。
先頭命令の固定AdvanceNonceAccount は必ず命令列の先頭に置く必要があります。ランタイムはこの位置でNonceトランザクションかどうかを判定します。
将来の廃止可能性公式ドキュメントに、Durable Nonceは将来のリリースで廃止される可能性があるとの注記があります（SIMD議論 #415）。設計に組み込む以上、代替手段（署名有効期間を短く切り、期限切れ時に自動で再クォートする）を併設しておくべきです。

② 手数料の負担者をどう設計するか

Solanaでは、トランザクションの手数料負担者（feePayer）は命令列の先頭アカウントであり、署名者のひとりです。DAMSをfeePayerに置いて部分署名すれば、利用者はSOLを1つも持っていなくても支払いができます。

これは訪日客にとって決定的です。取引所からPhantomにUSDCだけを引き出した利用者は、SOLの残高がゼロであることがよくあります。手数料自体は1件あたり0.000005 SOL程度でごく僅かですが、ゼロでは送れません。ATMの前で「SOLが足りません」と表示されるのは、体験として最悪の部類です。

ただし後述するとおり、Solana Payのトランザクションリクエスト仕様では、ウォレット側がfeePayerを利用者のアカウントに上書きすると読める記述があります。この場合はDAMSによる肩代わりが効かなくなるため、Solana Foundationのフィーペイヤー標準であるKoraなどのペイマスター経由での肩代わりを検討することになります。

④ ネイティブUSDCの識別

Solana上にはブリッジ経由のUSDC（Wormhole版など）も流通しています。これらは別のミントアドレスを持つ別トークンです。Circle発行のネイティブUSDCのミントアドレスをアプリ・バックエンドの両方で固定してください。

加えて、転送命令には transfer ではなく transferChecked を使います。ミントと小数桁数を命令内で検証するため、桁誤りによる事故を構造的に防げます。USDCは6桁です。

方式A：自前署名方式ATMカメラ必要

DAMSがトランザクションを組み立て、feePayerとして部分署名し、利用者の署名だけをATMで受け取る。送信はDAMSが行う。

EVM版のEIP-3009方式と設計思想は同じです。違いは、署名対象が構造化データではなくトランザクションそのものである点。命令の中身がすべて署名対象に含まれるため、金額・宛先・トークンの取り違えが構造的に起きません。

Transaction
  feePayer:  DAMS_FEE_PAYER       // ガスをDAMSが負担 → 利用者はSOL不要
  nonceInfo: {
    nonceAccount:   NONCE_POOL_017  // セッションごとにプールから確保
    nonceAuthority: DAMS_AUTHORITY  // DAMSが一方的に無効化できる
    nonce:          <durable nonce> // 有効期限なし
  }
  instructions: [
    0: System.advanceNonce          // 必ず先頭に置く
    1: Token.transferChecked {
         source:      USER_USDC_ATA
         mint:        EPjFW…TDt1v      // ネイティブUSDCに固定
         destination: DAMS_USDC_ATA
         owner:       USER_PUBKEY
         amount:      206_140_000      // 206.14 USDC
         decimals:    6                // 桁誤りを命令側で検証
       }
    2: Memo { referenceId: "ATM-8842-01F3" }
  ]
  signatures: [
    DAMS_FEE_PAYER  ✓ 事前に部分署名済み
    USER_PUBKEY     ← ATMで取得する唯一の署名
  ]

利用者が承認するのは1つの署名だけ。その署名対象にfeePayer・ミント・金額・宛先がすべて含まれているため、EVM版で必要だったchainIdの明示的な確認すら不要になる。

シーケンス

EVM版と同じく、払出しの可否を確定させてから送信する。異常時はNonceを進めるだけで署名済みトランザクションが無効になるため、後始末が単純。

方式B：Solana PayATM改修は最小

ATMは solana: で始まるURLをQRとして表示するだけ。読取機構は不要です。

Solana Payは、Solanaのトランザクションリクエストをそのままログにするための公開仕様です。BIP 21とEIP 681を参考に設計され、Phantomをはじめとする主要ウォレットが実装しています。QRコードやNFCタグに埋め込んで、支払いの要求やトランザクションの組み立てに使えます。

ここがEVM版との決定的な違いです。WalletConnect Payのような外部の決済網に加盟する必要がなく、DAMSが自分のサーバに仕様どおりのエンドポイントを立てるだけで成立します。加盟店手数料もかからず、日本での提供可否を照会する必要もありません。

トランザクションリクエストの流れ

URLは solana: の後にHTTPSのURLを置く形式です。ウォレットはそのURLに対してHTTPリクエストを行い、トランザクションを組み立てます。仕様上、まずGETで表示用のラベルとアイコンを取得し、次にPOSTで利用者のアカウントを送ってきます。DAMSはそれを受けてトランザクションを構築し、base64でシリアライズして返します。

利用者が支払ったことをDAMSが検知する仕組みが reference です。署名者ではないアカウントとしてトランザクションに含めておくと、findReference でそのトランザクションを特定でき、validateTransfer で宛先と金額が期待どおりかを検証できます。ATMは決済IDを一切扱わず、referenceの検出だけで排出判定ができます。

15でDAMSの手を離れる。だから4と5を6より前に置く。EVM版のWalletConnect Payと同じ構造だが、間に立つのは外部事業者ではなくウォレット自身。

仕様の読みに曖昧さがある。実装前に検証してください

Solana Pay v1.1の仕様には、トランザクションリクエストにおいてウォレットはトランザクション内のfeePayerを無視してリクエスト中のアカウントに設定し、recentBlockhashも無視して最新のものに設定しなければならないという記述があります。文字どおりなら、DAMSによるガス肩代わりもDurable Nonceも効きません。

一方で、同じ仕様群にはアプリケーションは部分署名または完全署名したトランザクションを返してよく、ウォレットはそれを信頼できないものとして検証しなければならないという記述もあり、部分署名を前提としたガイドも複数存在します。バージョン間の差か、節ごとの適用範囲の違いと思われます。

Phantomなど対象ウォレットの実機で、DAMSをfeePayerにした部分署名済みトランザクションが通るかを最初に検証してください。通らない場合は、Solana Foundationのフィーペイヤー標準であるKoraのようなペイマスター経由での肩代わりに切り替えます。ペイマスターは利用者がSOLを1つも持たない口座から送金でき、手数料をUSDCなどで支払える仕組みを提供します。

Solanaで進めるなら、方式Bから入るのが合理的

EVM版で方式Bを勧めにくかった理由が、Solanaでは消えています。WalletConnect Payに依存することの代償——0.5〜1.0％の手数料、日本での提供可否の不確実性、仕様変更が外部判断になること——が、Solana Payでは一切発生しません。公開仕様をDAMSが自分で実装するだけです。

ATM側への要求もQR表示だけで、セブン銀行との協議は最も軽い形になります。確定待ちも1〜2秒と短く、EVM版で懸念した「30秒の沈黙」も起きません。

ただしfeePayerとDurable Nonceの扱いを実機で検証するのが先です。ここが仕様どおりに「ウォレットが上書きする」なら、利用者にSOL残高を要求することになり、訪日客向けとしては成立しません。その場合はペイマスターを噛ませるか、方式Aに倒します。

チェーン選択そのものの判断

EVM版とSolana版のどちらを本線にするかは、技術ではなく訪日客のUSDC保有実態で決まります。取引所からどのチェーンで引き出しているか、どのウォレットを使っているか。ここは調査が先で、設計の優劣で決める話ではありません。

両対応も可能です。事前登録で利用者にチェーンを選ばせ、ATM画面では同じ導線に見せる。ただし決済アダプタが2系統になるため、開発と運用の負荷は素直に2倍近くになります。POCの段階では片方に絞ることを勧めます。
