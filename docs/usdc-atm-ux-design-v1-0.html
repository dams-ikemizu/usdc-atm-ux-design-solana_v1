前提

4つの判断が、両方式に共通してかかっています。

判断内容理由
カストディしないUSDCは利用者のアドレスに置かれたまま。DAMSは預からない。返金対応を構造的に避ける。日本円の預かり負債も発生させない。
旅券は事前に1回読取は事前登録時のみ。ATMでは読ませない。記録要件は属性の保存であり、取引ごとの再取得は不要。ATM前で旅券を出させる動作は最大級の離脱要因になる。
MRZ撮影で足りるICチップ読取ではなくカメラでのMRZ読取を採用。ブラウザから旅券チップのAPDU通信ができず、ネイティブアプリ配布が必須になる。訪日客に入国直後のアプリ導入を求めるとファネルが折れる。
払出しを先に確定資産が動く前に、ATMが紙幣を出せる状態かを確認する。現金は出たら取り消せない。この順序だけで、返金ケースを物理故障に限定できる。

記録要件は旅券MRZの3か所で満たせる

記録が必要なのは氏名・国籍・生年月日の3項目です。これらはすべて旅券下部のMRZ（機械読取領域）に固定位置で格納されています。ICAO 9303 TD3形式、2行×44文字。

1行目  P<JPNYAMADA<<HANAKO<<<<<<<<<<<<<<<<<<<<<<<<<
2行目  TR12345678JPN9204141F3304147<<<<<<<<<<<<<<02

       氏名 = 1行目 6〜44桁（姓<<名、39文字で打ち切り）
       国籍 = 2行目 11〜13桁（ICAO 3文字コード）
       生年月日 = 2行目 14〜19桁（YYMMDD、世紀情報なし）

重み7,3,1を巡回させるチェックディジットが旅券番号・生年月日・有効期限・全体にそれぞれ付いている。生年月日を1文字誤読すれば90%の確率でその場で検出できるため、撮影UIにシャッターボタンを置かずに済む。

MRZ読取は本人性を検証しない

券面に印字された文字列を読むだけであり、旅券の真正性も、提示者が名義人であることも検証しません。ICチップのBAC/PACE認証を通せば前者は検証できますが、それにはネイティブアプリが必要です。この設計は記録要件を満たすことを目的とし、偽造検知は目的としていません。

MRZ読取の実装で詰まる箇所

問題内容対処
ラミネート反射保護フィルムが光源を反射し、MRZ帯が白飛びする。読取失敗の最大要因。フラッシュを強制オフ。輝度ヒストグラムを監視し、飛んでいたら傾けるよう促す。複数フレームの多数決で確定。
世紀の曖昧さ生年月日はYYMMDDのみで、1900年代か2000年代かの情報がない。有効期限から範囲を絞り、確認画面で西暦4桁を表示して目視させる。自動確定させない。
氏名の打ち切り氏名欄は39文字。長い氏名は途中で切られ、ミドルネームが欠落する。券面のとおりに記録する仕様であることを明示。打ち切り時は確認画面で注記する。
文字の混同OCR-Bでも 0/O、1/I、5/S、8/B の誤読が起きる。桁ごとに期待される文字種が決まっているため候補を制限する。残りはチェックディジットで弾く。
端末側の処理画像をサーバに送ると、通信が細い環境で待ち時間が発生する。WebAssembly版のMRZ SDKでブラウザ内完結にする。画像が端末を出ないため確認画面でその旨を伝えられる。
旧様式・他国旅券2020年2月以前の旅券や、日本以外の旅券も対象になる。MRZ仕様は共通のため差分はない。一部の国は任意欄の使い方が異なるが、3項目の取得には影響しない。

方式A：自前署名方式ATMカメラ必要

USDCのコントラクトが実装するEIP-3009を使い、ATMの前で署名だけをさせる。トランザクションの送信はDAMSが握る。

紙幣を出せなかったなら署名を捨てるだけでよく、資産は一度も動きません。ガス代はDAMSが負担するため、利用者はUSDCだけを持っていればよく、ネイティブトークンを用意する必要がありません。

domain: {
  name:              "USD Coin"
  version:           "2"
  chainId:           8453   // Base — 署名対象なのでチェーン誤りが起きない
  verifyingContract: 0x8335…2913
}
primaryType: ReceiveWithAuthorization  // Transferではなくこちら
message: {
  from:        0x91c4…7Ae1  // 利用者
  to:          0x7A3f…c19B  // DAMS
  value:       206140000  // 206.14 USDC — 署名がレートロックの実体
  validAfter:  0
  validBefore: 1772605380 // +180秒で自動失効
  nonce:       0x4f8a…1d02  // DAMSが生成する32バイト乱数
}

ReceiveWithAuthorization は呼び出し元が受取人と一致することを要求するため、署名QRを第三者に撮影されても、そのまま実行されることはない。

シーケンス

17と19の間に18が入っていることが要点。払出しの可否を確定させてからトランザクションを送るため、資産が動いた後に現金が出せない状態がほぼ発生しない。

実装上の注意

項目内容
nonce消費≠入金完了最重要。署名者は自分のnonceを焼けます。cancelAuthorizationを呼ぶか、同じnonceを自己送金で消費してリレーヤーとレースすればいい。結果、nonceは「使用済み」と読めるのに資金は届いていない状態が起こります。決済確認に authorizationState を使わず、必ずトランザクションのレシートとTransferイベントで判定してください。
ネイティブUSDCのみPolygonのブリッジ版USDC（USD Coin (PoS)）はEIP-3009非互換で transferWithAuthorization が使えません。Circle発行のネイティブUSDCに限定し、アプリ側でトークンアドレスを固定します。
ハードウェアウォレット不可MetaMask経由のTrezorやLedgerは personal_sign のみで、EIP-712署名ができません。このフローから外れるため、エラー時の案内文言を用意します。
EIP-1271 / 6492スマートコントラクトウォレットからの署名はECDSAではなくEIP-1271で検証します。カウンターファクチュアルなウォレットにはEIP-6492が要ります。内蔵ウォレットをEOAで作るなら当面不要。
送信アカウントの並列度単一のEOAから送信するとnonce競合でスループットが頭打ちになります。送信用アカウントをプール化し、ATM単位またはシャード単位で割り当てます。
署名画面の可読性内蔵ウォレットを採る最大の理由。「206.14 USDCを支払い、￥30,000を受け取る」と日英で表示し、16進数のアドレスやtyped dataの生データを見せません。
QRの物理条件署名要求は約200バイト、署名は65バイト。いずれも静的QR1枚に収まります。誤り訂正レベルはH。ATM画面のガラス反射とスマホ画面への近接ピントが実地の主な失敗要因です。

失敗はほとんど資産が動く前に起きる

方式B：WalletConnect PayATM改修は最小

加盟店として決済を作成し、リンクをQRとして表示するだけ。ATM側の追加ハードウェアは要りません。

WalletConnectは700以上のウォレット、5億人以上のユーザーをつなぐネットワークで、2025年の取引額は4,000億ドル超。WalletConnect Payはその上に載る決済プロダクトです。標準フローはEIP-3009のtyped-dataペイロードに署名させる方式で、方式Aと暗号面では同じ仕組みを使います。

前例として、Ingenicoが2026年1月に実店舗POSへ導入しています。ハードウェア変更は不要で、Androidの決済端末へのソフトウェア配信だけで済んだと報じられています。セブン銀行との協議では、この事例が説得材料になります。

3層構造。DAMSがどこに座るか

レイヤー役割
WalletConnect Payネットワーク、決済実行、精算基盤。
Enabling Party（PSP）加盟店を束ねる。WCPネットワーク手数料はWCPとこの層の間で別途の商業契約により合意され、WCPは原則として加盟店と直接の手数料関係を持たないとされています。
加盟店実際に決済を受ける事業者。DAMSが単純に入るならここ。
 DAMSが加盟店として入るのか、日本のEnabling Partyになるのかは別の戦略判断。後者ならATM1件ではなく、日本国内でWalletConnect Pay決済を提供する立場になる。

シーケンス

14がDAMSの手を離れているため、4と5を6より前に置いて失敗確率を物理故障だけに絞り込む。自前方式では排出2秒前だった確認が25秒前になるが、ATMは同時に1人しか操作しないためカセット残量は変化しない。

押さえるべき数字と制約

項目内容
加盟店手数料WalletConnectのPSP向け解説では0.5〜1.0%とされています（カードの2.5〜3.5%との比較として提示）。￥30,000なら150〜300円。利用者側は取引手数料なしでWCTのキャッシュバックを受け取ります。ボリュームディスカウントもあるとのこと。
確定時間 2〜30秒オンチェーン確定はネットワークにより2〜30秒。Ethereumメインネットで払われるとATMの前で30秒沈黙します。受け付けるチェーンをBase・Optimism・Arbitrumなど高速なものに絞ってください。
法定通貨精算はUSD/EURのみオフランプ提携先経由での提供で、日本円の精算はありません。DAMSはUSDCで受け取り、自分で円転してATMの現金を補充します。この回転日数がそのまま運転資本になります。
対応チェーンローンチ時はEthereum、Base、Polygon、Optimism、Arbitrum。Solanaはロードマップとされていましたが、現在のドキュメントにはSolana対応の実装ガイドとCAIP-19識別子が存在します。進行中とみて最新の対応表を直接確認してください。
CEX残高から払える中央集権取引所の統合により、利用者はCEXの口座残高から直接支払えます。自己管理ウォレットを持たない訪日客も対象にできるため、母集団が大きく広がります。
利用者情報の収集トラベルルール対応として氏名・生年月日を収集する仕組みがあり、ホストされたWebViewフォームで処理されます。DAMS側のMRZ読取と重複する可能性があります。二重入力を避ける整理が必要です。
返金API全額返金を要求するエンドポイントがあり、二重呼び出しは409で弾かれます。返金が例外処理ではなく標準機能として組み込めます。
ガス代ブロックチェーン側で決まり、WCPもEnabling PartyもOfframp Providerも制御しないと明記されています。高騰時の扱いは自分で設計する必要があります。

Tap to Pay という将来の選択肢

POS端末が pay.walletconnect.com を指すURIレコードを持つNDEFタグを発信し、スマホをかざすとウォレットが起動する方式があります。iOSはバックグラウンドタグ読取により、ロック画面やホーム画面からでも自動で読み取ります。QRの読み書きが一切不要になり、体感時間が最短になります。ただしWalletConnect側で実験的機能とされ、実装前に先方チームへの連絡が求められています。ATM側のNFC発信能力が前提になるため、当面は将来の拡張として位置づけます。

どの調査結果で、どちらに倒れるか

3つのうち1つでも「いいえ」なら方式A。すべて「はい」なら方式B。共通部分は先に作り切れるため、この分岐が確定する前でも開発は進められる。

現時点の暫定推奨は方式B。ただし前提が1つ未確認

方式BはATMへの要求がゼロです。既存のスマホATMと同じ「画面にQRを出す」だけで成立するため、セブン銀行との協議で最も通しやすく、カメラ転用の可否という不確実性に設計全体が人質に取られません。対象ユーザーも桁違いに広がります。

ただし、日本でWalletConnect Payが加盟店向けに提供されているかを、まだ確認できていません。ドキュメントは英語圏中心で、日本のEnabling Partyの存在も見当たらず、法定通貨精算がUSD/EURのみという点も、日本市場が現時点の主戦場ではないことを示唆します。ここが「未提供」なら推奨は方式Aに戻ります。

したがって、共通部分（事前登録・MRZ読取・ATM画面の骨格・払出し可否の事前確認）を先に作り切り、決済部分だけを差し替え可能な設計にしておくのが最も損の少ない進め方です。認証・決済手段を抽象化したインターフェースを1枚挟んでおけば、どちらに倒れても書き直しは決済アダプタだけで済みます。

高速チェーンのみを受け付ける設定が加盟店側でできるか。できないとATM前で30秒待たされる。
情報収集データの受け渡し
WalletConnect
フォームが収集した氏名・生年月日が加盟店に渡るのか。国籍は収集項目に含まれるか。渡らないならMRZ読取は残す。
決済キャンセルの有効範囲
WalletConnect
キャンセル用エンドポイントは署名提出後のどの段階まで有効か。ATM障害検知から間に合うか。
払出し可否の事前照会
セブン銀行
カセット残量や金種在庫を排出前に照会できるか。両方式で必要。
QR表示の自由度
セブン銀行
任意の文字列をQR化して画面表示できるか。既存スマホATMのQRが固定フォーマットの可能性がある。
カメラの用途拡張
セブン銀行
方式A限定。第4世代ATMのFACE CASH用カメラでスマホ画面のQRを読めるか。
ATMコーナーの電波
実測
方式選択そのものを左右する。設置場所を数十箇所サンプリングする。

試算
決済手数料、ガス代、ATM払出し手数料、円転コスト、運転資本。￥10,000の換金で成立するかを確認する。
